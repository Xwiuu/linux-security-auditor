# Module Communication Contracts & Versioned Schemas

**Status:** Proposed Standards  
**Version:** 1.0.0  
**Phase:** Sprint 00 Analysis  
**Engineering Policy:** Strict YAGNI & Explicit Schemas  

---

## 1. Inter-Module Communication Principles

To allow Bash, Perl, and future components to collaborate without tight coupling, cross-boundary communication follows three principles:

1. **Standardized Process Execution & Exit Codes:** Predictable CLI semantics across all languages.
2. **Standard JSON Envelope:** Structured machine outputs share a top-level metadata wrapper containing component ID, timestamp, schema version, execution status, and payloads.
3. **Strict Backward Compatibility:** Older consumers reading newer outputs or newer consumers reading legacy Bash outputs will not break if unmapped fields are encountered.

---

## 2. Standardized Exit Codes & Timeout Policy

All tools in the platform (`lsa`, `sec-cli`) adhere to the following exit code specification:

| Exit Code | Semantic Meaning | Description |
|---|---|---|
| `0` | **Success / Clean** | Operation succeeded. For audits, indicates zero High or Critical findings. |
| `1` | **Warning / Findings Detected** | Operation completed, but security findings (High/Critical) were identified. |
| `2` | **CLI Usage Error** | Invalid flags, missing required options, or malformed syntax. |
| `3` | **Environment / Dependency Failure** | Required system binary missing, insufficient privilege, unreadable path. |
| `124` | **Timeout** | Operation exceeded the configured deadline and was aborted. Used **only** when an actual timeout condition has been established. |

### Timeout Enforcement Policy
- **TCP Connect Timeout:** Default is 3 seconds; maximum configurable is 10 seconds.
- **DNS Resolver Timeout:** Implementation-dependent. Because blocking system resolver calls (such as C library `getaddrinfo`) cannot be guaranteed to terminate on a hard deadline across all libc/thread implementations, application timeout requests must not be described as guaranteeing a hard deadline without verified low-level support.
- Exit code `124` is returned only when an actual timeout condition has been established.

## 3. Top-Level Platform JSON Envelope

Every component supporting structured output formats produces a root envelope matching the following structure:

```json
{
  "$schema": "https://lsa.security/schemas/envelope.v1.json",
  "schema_version": "1.0.0",
  "component": "sec-cli",
  "command": "hash",
  "timestamp": "2026-10-29T12:00:00Z",
  "target_host": "edge-node-01.internal",
  "status": "success",
  "exit_code": 0,
  "data": {},
  "errors": []
}
```

- `schema_version`: String SemVer of the contract.
- `component`: String identifier (`lsa-bash`, `sec-cli`, `lsa-collector`).
- `command`: Specific sub-action performed.
- `timestamp`: UTC ISO-8601 timestamp.
- `status`: Enum string: `"success"`, `"warning"`, `"error"`, `"timeout"`.
- `exit_code`: Numeric exit code matching the table above.
- `data`: Component-specific payload.
- `errors`: Array of error strings or structured diagnostics (empty on success).

## 4. Versioned JSON Schemas

### 4.1. Current Bash Findings Schema (`findings.v1.json`)

This schema formally codifies the existing output generated by `reporters/json.sh`. It remains unchanged to preserve existing integrations. Note that as confirmed in the audit, the v1.0.0 Bash output does not include a root-level `schema_version` field.

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "LSA Findings Report v1",
  "type": "object",
  "required": ["findings"],
  "properties": {
    "findings": {
      "type": "array",
      "items": {
        "type": "object",
        "required": [
          "id",
          "category",
          "severity",
          "title",
          "description",
          "expected",
          "actual",
          "recommendation"
        ],
        "properties": {
          "id": { "type": "string", "pattern": "^[A-Z0-9_-]+$" },
          "category": { "type": "string" },
          "severity": {
            "type": "string",
            "enum": ["PASS", "INFO", "LOW", "MEDIUM", "WARN", "HIGH", "CRITICAL"]
          },
          "title": { "type": "string" },
          "description": { "type": "string" },
          "expected": { "type": "string" },
          "actual": { "type": "string" },
          "recommendation": { "type": "string" }
        }
      }
    }
  }
}
```

*Example Output:*
```json
{
  "findings": [
    {
      "id": "USER-001",
      "category": "users",
      "severity": "PASS",
      "title": "Only root has UID 0",
      "description": "No additional accounts with UID 0 were detected",
      "expected": "Only root should have UID 0",
      "actual": "root",
      "recommendation": "No action required"
    }
  ]
}
```

### 4.2. Security Engineering Operations Schema (`sec-ops.v1.json`)

Used by the Perl `sec-cli` tool for DNS, TCP, hashing, and structured logging.

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "Security Engineering Operations Schema v1",
  "type": "object",
  "required": ["schema_version", "component", "command", "timestamp", "status", "data"],
  "properties": {
    "schema_version": { "type": "string", "const": "1.0.0" },
    "component": { "type": "string", "const": "sec-cli" },
    "command": {
      "type": "string",
      "enum": ["dns", "tcp-check", "hash", "log", "integrity-init", "integrity-verify"]
    },
    "timestamp": { "type": "string", "format": "date-time" },
    "status": { "type": "string", "enum": ["success", "warning", "error", "timeout"] },
    "exit_code": { "type": "integer" },
    "data": { "type": "object" },
    "errors": {
      "type": "array",
      "items": { "type": "string" }
    }
  }
}
```

#### Payload: `hash`
```json
{
  "file_path": "/etc/ssh/sshd_config",
  "algorithm": "sha256",
  "hash": "b2c011e4f6057bc66b262d2da88d22d257bc5375fc1b8e668480d0d8beeb7b17",
  "size_bytes": 3280,
  "modified_epoch": 1729000000
}
```

#### Payload: `tcp-check`
```json
{
  "target_host": "10.0.0.1",
  "port": 22,
  "reachable": true,
  "latency_ms": 1.45,

}
```

#### Payload: `dns`

### 4.3. Infrastructure Collector Schema (`collector.v1.json` - Tentative)

Tentative schema for future native collectors extracting read-only system telemetry.

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "LSA Infrastructure Collector v1 (Tentative)",
  "type": "object",
  "required": ["schema_version", "component", "timestamp", "host_metrics"],
  "properties": {
    "schema_version": { "type": "string", "const": "1.0.0" },
    "component": { "type": "string", "const": "lsa-collector" },
    "timestamp": { "type": "string", "format": "date-time" },
    "host_metrics": {
      "type": "object",
      "properties": {
        "hostname": { "type": "string" },
        "uptime_seconds": { "type": "integer" },
        "load_averages": {
          "type": "array",
          "items": { "type": "number" },
          "minItems": 3,
          "maxItems": 3
        },
        "memory": {
          "type": "object",
          "properties": {
            "total_bytes": { "type": "integer" },
            "available_bytes": { "type": "integer" }
          }
        }
      }
    }
  }
}
```
